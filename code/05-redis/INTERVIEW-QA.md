## 🔥 第一组：性能本质（开胃题）

### ❓ Redis 为什么快？

> ↓ **答**（从 4 个维度答）：

1. **内存操作** — 数据全在内存里，纳秒级读写（vs MySQL 磁盘毫秒级）
2. **单线程** — 避免锁竞争、上下文切换、并发 bug
3. **IO 多路复用** — 一个线程监听多个 socket，epoll 机制高效
4. **高效数据结构** — SDS（O(1) 取长度）、hashtable、skiplist、listpack 等自研结构

加分项：RESP 协议解析简单、C 语言贴近底层、请求/响应模型（无锁）

> ⭐ **金句**："**内存 + 单线程 + IO 多路复用 + 高效数据结构**——四个加起来就是快。"

### ❓ Redis 是单线程吗？

> ↓ **答**（分场景答，不要一刀切）：

- **网络 IO（接收请求 + 解析 + 执行 + 写回）** → **单线程**
- **持久化（RDB / AOF rewrite）** → 子进程（fork）
- **异步删除（unlink / flushall async）** → 4.0+ 后台线程
- **网络 IO 读写** → 6.0+ **可选多线程**（默认关闭）

> ⭐ **金句**："Redis 的**核心命令执行是单线程**，避免锁；持久化和大 key 删除在**子进程/异步线程**里做；6.0 之后 IO 读写**可开多线程**但执行还是单线程。"

### ❓ Redis 6 为什么又有多线程？

> ↓ **答**：

- 6.0 之前：单线程**同时**负责网络 read + 命令执行 + 网络 write
- 6.0 之后：把**网络 read/write 拆分到多线程**，命令执行还是单线程
- 配置：`io-threads 4`（默认 1 = 关闭）
- 适用场景：**大 value（KB+）** 或 **QPS 极高** 时收益明显
- 小 value（默认 44 字节）反而**可能更慢**（多线程调度开销）

> ⭐ **金句**："6.0 多线程是**IO 多线程**，不是执行多线程——执行还是单线程避免数据竞争，本质是解决大 value 的网络读写阻塞。"

### 📝 补充题

- **Q：IO 多路复用是什么？epoll vs select？**
  > A：一个线程同时监听多个 socket。三种实现：select（轮询 O(N)）、poll（同 select）、epoll（事件驱动 O(1)，Linux）。Redis 在 Linux 用 epoll，在 BSD/macOS 用 kqueue。
- **Q：为什么单线程能避免锁竞争？**
  > A：单线程天然串行，所有共享数据无需加锁 → 实现简单、无死锁、无并发 bug、性能稳定。代价是**无法利用多核 CPU**（所以 6.0 才在 IO 层开多线程弥补）。

## ⭐ 第二组：数据类型与场景

### ❓ Redis 五种数据类型？

> ↓ **答**（按"底层 + 场景"答，比"答 String/List/Hash/Set/ZSet"更高级）：

| 类型 | 底层 | 复杂度 | 典型场景 |
|------|------|--------|----------|
| **String** | SDS（int/embstr/raw）| O(1) | 缓存、计数器、分布式锁、Session |
| **List** | quicklist（双向链表+listpack节点）| 头尾 O(1)，中间 O(N) | 消息队列、栈、最新列表 |
| **Hash** | listpack 小 / dict 大 | O(1) | 对象存储、用户资料、购物车 |
| **Set** | intset 小 / dict 大 | O(1) | 去重、共同好友、抽奖 |
| **ZSet** | listpack 小 / skiplist+dict 大 | O(log N) | 排行榜、延迟队列、滑动窗口限流 |

> ⭐ **金句**："五大基础类型外还有 **3 大特殊**：**Bitmap**（位操作，签到/日活）、**HyperLogLog**（UV 估算，误差 < 1%）、**GEO**（地理位置，基于 ZSet 实现）。"

### ❓ Hash、Set、ZSet 分别适合什么场景？

> ↓ **答**（按业务场景反推）：

**Hash**（字段级 KV）：
- ✅ 字段**经常变**的对象（用户资料、购物车、配置）
- ❌ 字段数 > 128（dict 占内存，不如 String + JSON）

**Set**（去重集合）：
- ✅ 去重、共同好友（SINTER）、推荐关注（SDIFF）、抽奖（SPOP）

**ZSet**（有序集合）：
- ✅ 排行榜、延迟队列、滑动窗口限流——**任何需要"按 score 排序"或"取 topN"**的场景

> ⭐ **金句**："**Hash 存对象、Set 去重、ZSet 排顺序**——记不住时按这三个关键词对号入座。"

### ❓ 为什么排行榜用 ZSet？

> ↓ **答**（5 点）：

1. **ZSet 按 score 排序** → `ZREVRANGE 0 9` 拿 top10 是 O(log N + M)
2. **score 可以是时间戳、点赞数、积分** → 任何"分值"都行
3. **ZINCRBY 原子加分** → 高并发下不会错
4. **O(log N) 增删改** + **O(log N) 范围查询** → 比 MySQL ORDER BY 快几千倍
5. **天然支持时间窗口**（score=时间戳）→ 延迟队列、滑动限流都能用

> ⭐ **金句**："排行榜用 ZSet 是因为**按 score 排序 + 范围查询 O(log N)**，而 MySQL 要全表扫或建索引还慢；ZSet 用**内存**换时间，常驻的 topN 缓存就特别合适。"

### 📝 补充题

- **Q：String 和 Hash 怎么选？**
  > A：字段**经常变** → Hash（HSET 单独改字段不序列化）；字段**稳定 + 整体读** → String + JSON（省 hash 元数据开销）。
- **Q：List 为什么不用做排行榜？**
  > A：List 是按**插入顺序**，不是按 score 排序；想 topN 要先 LRANGE 全量再排，O(N log N)。
- **Q：ZSet 元素很多时性能？**
  > A：默认 > 128 元素升级为 skiplist + dict，O(log N) 排序 + O(1) 查分数。百万级 ZSet 仍很快（内存够的前提下）。

## ⭐ 第三组：持久化（必问）

### ❓ Redis 为什么需要持久化？

> ↓ **答**：

- 内存数据**断电即失**，重启要恢复
- 主从复制依赖 RDB（全量同步）
- 即使是缓存，关键数据（订单、支付）丢了也不行
- Redis 提供两种机制：**RDB 快照 + AOF 日志**

> ⭐ **金句**："Redis 是内存数据库，**不持久化 = 裸奔**。RDB 是'定时拍照'，AOF 是'记流水账'。"

### ❓ RDB 和 AOF 怎么选？

> ↓ **答**（对比表）：

| 维度 | **RDB**（快照）| **AOF**（追加日志）|
|------|---------------|-------------------|
| 原理 | fork 子进程把内存**全量 dump** 到 rdb 文件 | 每条写命令**追加**到 aof 文件 |
| 文件大小 | 小（压缩二进制）| 大（文本/二进制命令）|
| 恢复速度 | **快**（直接加载）| **慢**（要重放命令）|
| 数据安全 | 可能丢最后一次快照后的数据 | 默认每秒 fsync，**最多丢 1 秒** |
| 性能影响 | fork 时**可能阻塞**（大内存 10ms+）| 每次写都 append，AOF rewrite 时阻塞 |
| 适用场景 | 备份、主从全量复制 | 数据不能丢（订单、支付）|

> ⭐ **金句**："**Redis 4.0+ 混合持久化 = RDB 全量 + AOF 增量**，既快又安全，**生产推荐**。"

### ❓ RDB 数据会丢失吗？

> ↓ **答**：

- **会**。RDB 是**定时**快照，默认配置下可能丢几分钟数据
- 触发时机：
  - `save m n` 规则（如 `save 3600 1` = 1 小时内 1 个 key 变 → 快照）
  - `BGSAVE`（后台）
  - `SHUTDOWN`（正常关服）
- 极端情况：刚做完快照 1 秒后服务器挂了 → 丢**最多 m 分钟 n 个 key** 的数据
- **想要更安全 → 加密 save 规则**（如 `save 60 100`）或**直接用 AOF**

> ⭐ **金句**："RDB 一定会丢数据，**最多丢 'm 分钟 × n 写' 的数据量**——想 0 丢失只能 AOF everysec 或 always。"

### ❓ AOF 一定不会丢数据吗？

> ↓ **答**（看配置）：

AOF 三种 fsync 策略：

| 策略 | 配置 | 丢失数据 | 性能 |
|------|------|----------|------|
| **always** | `appendfsync always` | **0 丢失**（每条命令都落盘）| 最差（同步 IO）|
| **everysec**（默认）| `appendfsync everysec` | **最多 1 秒** | 折中（推荐）|
| **no** | `appendfsync no` | **看 OS**（一般 30 秒）| 最好 |

- 真正的"0 丢失"只能 `appendfsync always`，但**性能差 10 倍**
- `everysec` 是工业级标准（兜底 1 秒）
- AOF 文件会无限增长 → **AOF rewrite**（重写压缩：把 100 个 INCR 写成 SET counter 100）

> ⭐ **金句**："AOF 默认 `everysec` 最多丢 1 秒；要 0 丢失用 `always` 但性能差；**混合持久化（RDB+AOF）是工业级最佳实践**。"

### 📝 补充题

- **Q：AOF rewrite 怎么做的？会阻塞吗？**
  > A：fork 子进程扫描内存生成新 AOF（只写最终状态，不写中间命令），期间新命令同时写到 old AOF + rewrite buffer；子进程完成后把 buffer 追加到新 AOF 并原子替换。**不阻塞主进程**（COW 机制）。
- **Q：bgsave 和 bgrewriteaof 能同时执行吗？**
  > A：不能。两个都是 fork 子进程，**CPU 和 IO 都会争抢**；Redis 用 `rdb_child_pid` 互斥，后到的会排队。
- **Q：混合持久化（Redis 4.0+）怎么工作？**
  > A：AOF 文件 = **RDB 格式的全量数据** + **AOF 格式的增量命令**。恢复时先加载 RDB 头（快），再重放 AOF 增量（数据全）。
- **Q：fork 阻塞怎么办？**
  > A：大内存（10GB+）fork 可能几十 ms。优化：① 用 `repl-backlog-size` 减少 fork 频率；② 避免 `always` 模式；③ 升级到 7.0+（多线程 AOF rewrite）。

## ⭐ 第四组：Key 过期 + 内存淘汰

### ❓ Redis Key 过期怎么删除？

> ↓ **答**（三种策略）：

1. **定时删除**（主动）：每个 key 设过期时启动一个定时器，**到期立刻删除**
   - 优点：内存友好（及时释放）
   - 缺点：CPU 不友好（大量 key 同时过期 → 定时器雪崩）
2. **惰性删除**（被动）：**访问 key 时才检查**过期，过期就删
   - 优点：CPU 友好
   - 缺点：内存不友好（大量过期 key 永远不访问 → 内存泄漏）
3. **定期删除**（折中）：**每隔 100ms 抽一批 key** 检查过期
   - 优点：折中
   - 缺点：频率难调

> ⭐ **金句**："Redis 用**惰性删除 + 定期删除**两种组合——访问时检查 + 定期抽样清理。**不靠定时器**，因为定时器太重。"

### ❓ 惰性删除？

> ↓ **答**：

- 触发时机：每次 `GET / HGET / LRANGE` 等**读命令** 时
- 流程：先看 expire dict 里的过期时间 → 已过期 → 同步删除 → 返回空
- 优点：**CPU 友好**（没访问就不付出）
- 缺点：**过期但没访问的 key 永远占内存**

> ⭐ **金句**："惰性删除就是**按需清理**——你不用它就赖着，你一用它就走。"

### ❓ 定期删除？

> ↓ **答**（具体机制）：

- 触发：每 100ms 一次的 serverCron 任务
- 流程：
  1. 从 `expires` 字典**随机抽 20 个** key
  2. 删掉其中**已过期**的
  3. 如果过期比例 > 25% → **立刻再抽 20 个** 处理（循环）
- 抽多少、抽几次：避免一次占太多 CPU
- 这是"**快慢模式**"：过期多时频繁清理，过期少时偶尔清理

> ⭐ **金句**："定期删除是**抽样清理 + 自适应频率**——20 个里过期超 1/4 就立刻再来一轮，直到过期少为止。"

### ❓ Redis 内存满了怎么办？

> ↓ **答**（看配置 + 行为）：

- **8 种淘汰策略**（`maxmemory-policy`）：

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `noeviction`（默认）| **不淘汰**，写命令返回 OOM 错误 | 不能丢数据 |
| `allkeys-lru` | 所有 key 里 LRU 淘汰 | **通用缓存**（推荐）|
| `allkeys-lfu` | 所有 key 里 LFU 淘汰（**Redis 4.0+**）| 热点数据明显 |
| `allkeys-random` | 随机淘汰 | 兜底 |
| `volatile-lru` | 设了过期的 key 里 LRU | 想保留永久 key |
| `volatile-lfu` | 设了过期的 key 里 LFU | 同上 |
| `volatile-random` | 设了过期的 key 里随机 | 同上 |
| `volatile-ttl` | 设了过期的 key 里 **TTL 最短** 的先淘汰 | 想优先清快过期的 |

- 推荐：**`allkeys-lru`**（缓存场景）/**`allkeys-lfu`**（热点明显）/ **`volatile-ttl`**（要保留某些 key 永不过期）

> ⭐ **金句**："默认 `noeviction`（不淘汰写会失败），生产要改成 **`allkeys-lru` 或 `allkeys-lfu`**——根据数据访问模式选。"

### ❓ LRU / LFU 怎么实现的？

> ↓ **答**：

**LRU**（Least Recently Used，最近最少用）：
- 理论上：用链表维护访问顺序，O(1) 更新
- Redis 实现：**近似 LRU**——每个 key 加一个 24 位时间戳字段，淘汰时**抽一批**对比时间戳
- 优点：实现简单（O(1) 字段更新，O(N) 抽样）
- 缺点：冷数据如果被偶然访问就"洗白"

**LFU**（Least Frequently Used，最不经常用，Redis 4.0+）：
- 字段：16 位**访问频率 counter** + 8 位**衰减时间**
- 衰减公式：`counter -= (now - last_decay) / lfu_decay_time`（默认 1 分钟）
- 优点：**真正抗偶然访问**（高频 key 不容易被一次访问就保护）
- 缺点：counter 会饱和 → Redis 用对数计数器

> ⭐ **金句**："Redis 的 LRU 是**近似 LRU**（不是真 LRU 链表）；LFU 在 LRU 基础上加了**衰减机制**——访问少会自然降权，避免偶然访问'洗白'冷数据。"

### 📝 补充题

- **Q：怎么计算 Key 实际占多少内存？**
  > A：`MEMORY USAGE key` 命令，返回字节数（含 SDS 头、dictEntry、链表指针等）。要算总用 `INFO memory` 看 `used_memory_human`。
- **Q：内存碎片率（mem_fragmentation_ratio）怎么看？**
  > A：INFO 里的 `mem_fragmentation_ratio = used_memory_rss / used_memory`，> 1.5 碎片严重，< 1 内存不足在用 swap。碎片严重可 `MEMORY PURGE` 或重启。
- **Q：SCAN 和 KEYS 区别？**
  > A：`KEYS *` 是 O(N) 阻塞；`SCAN 0 COUNT 100` 是游标式**渐进遍历**，不阻塞（生产用 SCAN）。

## 🔥 第五组：缓存三大问题（超高频）

> 这一组**必背**，基本每场 Redis 面试都问。

### ❓ 什么是缓存穿透？

> ↓ **答**：

- **场景**：查询一个**根本不存在**的数据（如 id = -1）
- **现象**：缓存没命中 → 查 MySQL → MySQL 也没有 → 不写缓存 → 每次都打到 MySQL
- **本质**：绕过缓存**直接打到 DB**

> ⭐ **金句**："穿透是**查不存在**——缓存和 DB 都没有，每次都打 DB。"

### ❓ 什么是缓存击穿？

> ↓ **答**：

- **场景**：某个**热点 key 过期瞬间**，大量请求同时来
- **现象**：100 个请求都发现 key 过期 → 100 个请求都打 DB
- **本质**：**单 key 过期 + 高并发**

> ⭐ **金句**："击穿是**单热点 key 过期瞬间被打爆**——1 个 key 引发雪崩。"

### ❓ 什么是缓存雪崩？

> ↓ **答**：

- **场景**：**大量 key 同时过期** 或 **Redis 挂了**
- **现象**：所有请求都没命中缓存 → 全部打 DB → DB 崩溃
- **本质**：**多 key 同时失效 + 高并发**

> ⭐ **金句**："雪崩是**大量 key 同时过期或 Redis 挂**——比击穿范围更广。"

### ❓ 分别怎么解决？

> ↓ **答**（按问题对号入座）：

#### 缓存穿透（查不存在）

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **空值缓存** | DB 查不到也写一个 `key=""` + 短 TTL | ✅ 简单；⚠️ 大量不同攻击 key 会占内存 |
| **布隆过滤器** | key 进 DB 前先过 Bloom Filter | ✅ 内存省；⚠️ 有误判（一般 1%），不能删 |
| **参数校验** | 业务层拦截明显非法的请求 | ✅ 最快；⚠️ 治标不治本 |

> 推荐：**布隆过滤器 + 空值缓存双保险**

#### 缓存击穿（单 key 过期）

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **互斥锁（分布式锁）** | 第一个请求拿锁查 DB 写缓存，其他等 | ✅ 一致性强；⚠️ 实现复杂，锁等待 |
| **逻辑过期** | value 里存 expire_time，过期了**异步重建** | ✅ 不阻塞；⚠️ 短期可能读到旧值 |
| **热点 key 永不过期** | 后台异步更新缓存，缓存本身不设 TTL | ✅ 简单；⚠️ 需保证更新链路 |

> 推荐：**互斥锁（强一致）/ 逻辑过期（高可用）**

#### 缓存雪崩（多 key 同时过期）

| 方案 | 做法 |
|------|------|
| **过期时间加随机值** | `expire = base + random(0, 300)` 错开 |
| **多级缓存** | Redis + 本地缓存（Caffeine/Guava）|
| **熔断降级** | Redis 挂了直接返回兜底数据 |
| **Redis 高可用** | 主从 + Sentinel + Cluster |
| **提前预热** | 大促前手动加载热点 key |

> 推荐：**过期时间加随机值（最简单）+ Redis 高可用**

> ⭐ **金句**："穿透→**空值缓存/布隆**；击穿→**互斥锁/逻辑过期**；雪崩→**过期加随机/高可用**。记不住就用一句话：**穿透是查不到、击穿是热点过期、雪崩是大量过期或宕机**。"

### 📝 补充题

- **Q：布隆过滤器 vs 空值缓存怎么选？**
  > A：误判敏感（支付）→ 空值；量大且允许小误判 → 布隆。**实际生产多组合用**：布隆挡大部分攻击 key + 空值兜底。
- **Q：逻辑过期怎么实现？**
  > A：value 是 JSON `{data: ..., expire_time: ...}`，**不带 TTL**。读时发现 expire_time 过了 → 返回旧值 + 异步线程重建缓存；写时用互斥锁防止并发重建。
- **Q：Redis Cluster 下雪崩会怎样？**
  > A：单个 master 挂了 → 槽位不可用 → 那部分 key 都打不到 → 等同于局部雪崩。解决：① 多副本（每 slot 多 replica）；② 客户端熔断（连不上就降级）。

## ⭐ 第六组：Redis 与 MySQL 一致性

### ❓ Redis 和 MySQL 如何保证一致性？

> ↓ **答**（直说：理论上做不到强一致，**只能最终一致**）：

- **强一致**（同步双写）→ 性能差（每次写 2 个库）
- **最终一致**（异步同步）→ 工业级方案，**业界主流**
- 三种典型方案：

1. **先更新 DB，再删缓存**（Cache Aside，最常用）
2. **延迟双删**（更新 DB 后删一次缓存，过几百 ms 再删一次）
3. **订阅 binlog 异步同步**（Canal 等中间件）

> ⭐ **金句**："**理论上做不到强一致**（CAP），业界都是**最终一致**：Cache Aside + 延迟双删 + binlog 订阅组合拳。"

### ❓ 为什么通常是更新 MySQL 后删除 Redis？

> ↓ **答**（"删"比"更新"好在哪）：

- **更新缓存的坑**：
  - 写多读少 → 缓存被反复覆盖但没人读 → 浪费
  - **并发写** 容易脏：两个线程同时 A 改 B 改 → 缓存可能是 B 但 DB 是 A
  - 写完 DB 还没更新缓存时读 → 读到旧缓存
- **删除缓存的好处**：
  - 下次读时**懒加载**（lazy load）→ 永远读到最新
  - 简单、不会有"覆盖顺序"问题
  - 唯一坑：删完到下次读之间可能短暂读到旧值（**最终一致**就能接受）

> ⭐ **金句**："**更新 DB 后删缓存**（Cache Aside）——删比改安全，下次读时懒加载，永远最新。"

### ❓ 删除 Redis 失败怎么办？

> ↓ **答**（三种兜底）：

1. **重试机制**（简单）
   - 删失败 → 放重试队列（本地内存队列/数据库任务表）→ 定时任务重试
2. **延迟双删**（折中）
   - 更新 DB → 删缓存 → 延迟 500ms → 再删一次
   - 解决：删完缓存后，DB 还没改完时，旧的"读请求"回填了旧值
3. **订阅 binlog 异步**（**最可靠**）
   - Canal 订阅 MySQL binlog → 解析 → 同步到 Redis
   - **删除缓存是同步的，但同步是异步的**（MQ 兜底）
   - 优点：彻底解耦 DB 和 Redis，强保证最终一致

> ⭐ **金句**："删失败 → **重试 + 延迟双删 + binlog 订阅**三层兜底，越往后越可靠。"

### ❓ 如何最终一致？

> ↓ **答**（最佳实践组合）：

```
[写入流程]
1. 写 MySQL (主)
2. 写 binlog (同步)
3. Canal 订阅 binlog
4. 异步删/更新 Redis
[如果 Canal 挂了] → 业务降级直接删缓存
[如果 Redis 删失败] → 重试队列
```

- 强保证："**binlog 是事实来源**（source of truth），Redis 只是缓存"
- 业务接受度：95% 场景能接受秒级不一致

> ⭐ **金句**："**最终一致 = DB 主写 + binlog 同步 + Redis 兜底**——把'真相'锁在 DB，把'展示'放缓存。"

### 📝 补充题

- **Q：延迟双删延迟多久？**
  > A：经验值 500ms-1s。要覆盖"主从复制延迟 + 读请求回填旧缓存"的时间窗。
- **Q：Canal 是什么？原理？**
  > A：阿里开源的 MySQL binlog 订阅中间件，把自己伪装成 MySQL slave 接收 binlog → 解析 → 投递到 MQ/RocketMQ → 消费者更新 Redis。**完全解耦业务**。
- **Q：能不能"先更新 Redis 再更新 DB"？**
  > A：能但**非常危险**。如果 DB 写失败 → Redis 新值 DB 旧值 → 不一致时间长。先 DB 后删缓存更安全。

## 🔥 第七组：分布式锁（最高频）

> 这一组你"正在学习"。

### ❓ Redis 如何实现分布式锁？

> ↓ **答**（基础版）：

```bash
SET key value NX PX 30000
```

- `NX`：只有 key 不存在才设（保证互斥）
- `PX 30000`：30 秒后自动过期（防死锁）
- **一条命令**搞定加锁+过期，**原子**（不会加完锁忘设过期）

> ⭐ **金句**："**SET key value NX PX 30000** 是分布式锁的最小可用实现。"

### ❓ SETNX 为什么不够？

> ↓ **答**（关键缺陷）：

```bash
SETNX key value        # 1. 加锁
EXPIRE key 30          # 2. 设过期（分两步！）
```

- **两条命令 → 不是原子**：
  - 加完锁后**进程崩溃** → 没设过期 → **死锁**
  - 设过期前**网络断开** → 同上
- 正确做法：**用一条 `SET key value NX PX 30000` 同时设值 + 过期**

> ⭐ **金句**："**SETNX + EXPIRE 两条命令有原子性 bug**——加锁成功但崩在 EXPIRE 前就死锁。**必须用 SET NX PX 一条命令**。"

### ❓ 为什么 Value 要 UUID？

> ↓ **答**（防误删）：

- Value = 当前进程唯一 ID（UUID / requestId）
- 解锁时**先 GET 校验是不是自己加的锁，再 DEL**：
  ```lua
  if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
  else
      return 0
  end
  ```
- 否则：A 加锁 → A 没释放 → 锁过期 → B 加锁 → A 醒过来 DEL → **把 B 的锁删了！**

> ⭐ **金句**："**Value = UUID 用于识别锁的所有者**——保证只删自己的锁，不误删别人的。"

### ❓ 为什么不能直接 DEL？

> ↓ **答**：

- 没有 UUID 校验 → 上面那个误删场景
- 没有原子性 → GET 和 DEL 之间锁可能过期被别人拿到 → DEL 删的是别人的锁
- 解决：必须用 **Lua 脚本**保证 GET + DEL 原子

> ⭐ **金句**："**直接 DEL = 不校验 = 误删别人锁**。必须用 Lua 原子化 GET+DEL。"

### ❓ Lua 脚本为什么必要？

> ↓ **答**：

- **Lua 脚本在 Redis 里单线程执行 → 天然原子**
- 把多步操作包成 Lua → 一次执行不会被别的请求打断
- 分布式锁的"**原子解锁**"必须用 Lua：
  ```lua
  if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('del', KEYS[1])
  end
  ```

> ⭐ **金句**："**Lua 是 Redis 内置的'事务'**——比 MULTI/EXEC 强（可传参、可读变量），分布式锁必用 Lua。"

### ❓ 锁续期怎么实现？

> ↓ **答**（看门狗机制）：

- **问题**：业务执行 30s 没完，锁过期自动释放 → 并发问题
- **解决**：后台线程**每隔 10s** 检查业务是否还在跑：
  - 在 → 续期（`PEXPIRE` 把过期时间推到 30s 后）
  - 完 → 立刻 DEL 释放
- **代表实现**：[Redisson](https://github.com/redisson/redisson) 的 `lockWatchdogTimeout`（默认 30s，每 10s 续到 30s）
- 自己实现：起个 goroutine 用 `time.Tick` 调 `PEXPIRE`

> ⭐ **金句**："**锁续期 = 看门狗（Watch Dog）**——业务没完就续命，Redisson 默认 30s 过期 + 10s 续期一次。"

### 📝 补充题

- **Q：Redlock 是什么？**
  > A：Redis 作者 antirez 提出的**多 master 集群锁**——N 个独立 master 都加锁成功才算成功（过半）。有争议：Martin Kleppmann 指出时钟跳跃等问题；业界实际用 Redisson 看门狗单 master 已够用。
- **Q：分布式锁还有什么方案？**
  > A：① **ZooKeeper**（临时顺序节点，强一致但写慢）；② **etcd**（lease + revision，类似 ZK）；③ **MySQL**（唯一索引，差但简单）；④ **Redisson**（Redis + 看门狗 + Redlock，业界最常用）。
- **Q：ZSet 怎么实现分布式锁？**
  > A：有点 hack——用 `ZADD` 加成员 + score=过期时间，但语义不清、释放麻烦，**不推荐**。
- **Q：集群下分布式锁有什么坑？**
  > A：① master 拿锁后**没同步到 replica** 就挂了 → 锁丢失（Redlock 部分解决）；② **大 key / 慢命令** 会阻塞所有锁请求。解决：用专门的 lock 实例（独立 Redis）。

## ⭐ 第八组：主从复制 + Sentinel

### ❓ Redis 主从复制？

> ↓ **答**（基本概念）：

- **一个 Master 写，多个 Replica 读**（读写分离）
- 复制流程：
  1. Replica 发 `PSYNC` → Master
  2. Master fork 子进程生成 **RDB** → 发给 Replica
  3. Replica 加载 RDB
  4. 期间 Master 的新写命令 → **repl_backlog**（环形缓冲区）
  5. Master 把新写命令**增量同步**给 Replica
- 全量 + 增量结合 = **部分重同步**（Redis 2.8+）

> ⭐ **金句**："**主从 = 一写多读**——Master 写、RDB 全量 + repl_backlog 增量同步给 Replica，读请求打到 Replica 减压。"

### ❓ Replica 能不能变 Master？

> ↓ **答**（能，需要"选主"机制）：

- **手动切换**：运维改配置，把 replica 提升为 master（停服）
- **自动切换**：用 **Sentinel**（自动选主 + 通知 + 故障转移）
- Replica 选举规则：
  1. **优先级**（`replica-priority`，默认 100，越小越优先）
  2. 复制偏移量最大（数据最新）
  3. runid 最小的
- 选完后 → `SLAVEOF NO ONE` 让它变 master，其他 replica 切到新 master

> ⭐ **金句**："Replica **能变 Master**，但需要有人帮它'上位'——手动或 Sentinel 自动。"

### ❓ Master 挂了怎么办？

> ↓ **答**（三步流程）：

1. **检测**：Sentinel 集群每 1 秒 PING Master，连续 5 次失败 → **主观下线（SDOWN）**
2. **确认**：集群过半数 Sentinel 认为它挂了 → **客观下线（ODOWN）**
3. **选新 Master**：按上面规则选 Replica + `SLAVEOF NO ONE` 提升
4. **通知**：客户端订阅 Sentinel → 拿到新 Master 地址 → 重连
- 整个过程**秒级**（默认 30s 内完成）

> ⭐ **金句**："**Master 挂了 → Sentinel 集群 ODOWN → 选 Replica 提升 → 通知客户端**——整个过程半自动、秒级完成。"

### ❓ Sentinel 是什么？

> ↓ **答**（核心要点）：

- **本质**：特殊的 Redis 进程（启动用 `redis-sentinel`），不存数据
- **三大职责**：
  1. **监控**（Monitor）：心跳检测 master/replica
  2. **通知**（Notify）：故障时通过 pub/sub 通知客户端
  3. **自动故障转移**（Automatic Failover）：选主 + 切换 + 配 client
- **最小集群**：3 个 Sentinel 节点（保证过半数）
- **最终一致性**：客户端订阅 Sentinel（`+switch-master` 频道）拿新地址

> ⭐ **金句**："Sentinel = **哨兵**——它不存数据，只负责**监控 + 选主 + 通知**，是 Redis 高可用的核心组件。"

### 📝 补充题

- **Q：主从复制延迟怎么办？**
  > A：① 强制读 master（高一致性场景）；② 业务容忍（电商详情可容忍秒级延迟）；③ 用**缓存一致性中间件**（如 Canal 监听 binlog 同步）。
- **Q：脑裂（split-brain）怎么解决？**
  > A：Sentinel 选新 master 时**老 master 还在接受写** → 脑裂。解决：① 客户端只连 Sentinel 拿的 master；② 配置 `min-replicas-to-write 1`（写 master 时至少 1 个 replica 同步完成）。
- **Q：复制风暴是什么？**
  > A：一个 master 带 N 个 replica → master 同时给 N 个发 RDB → IO 打满。解决：**级联复制**（master → 中间 replica → 其他 replica）。

## ⭐ 第九组：Redis Cluster

### ❓ Redis Cluster 是什么？

> ↓ **答**：

- **Redis 官方分布式方案**（3.0+），解决单实例**内存 + 并发**上限
- **数据分片**：16384 个 slot 分散到多个 master
- **去中心化**：节点间通过 **Gossip 协议** 通信，无中心节点
- **自动故障转移**：每个 master 有多个 replica，master 挂了 replica 顶上
- 客户端连任意节点，**重定向**到正确节点

> ⭐ **金句**："**Cluster = 数据分片 + 主从 + 故障自动转移**——把数据按 slot 切片分散到 N 个 master，每个 master 有 replica 兜底。"

### ❓ 为什么需要 Cluster？

> ↓ **答**（3 个核心问题）：

1. **单实例内存瓶颈**：64GB 上限（操作系统 / 协议开销）
2. **单实例 QPS 瓶颈**：单线程 ~10 万 QPS，再高扛不住
3. **单点故障**：Sentinel 只解决 HA，**不解决水平扩展**

> ⭐ **金句**："Sentinel 是**垂直扩展 + 高可用**，Cluster 是**水平扩展 + 高可用**——上 T 数据、上百万 QPS 必须用 Cluster。"

### ❓ 为什么是 16384 个 Slot？

> ↓ **答**（面试要答出为什么是 2 的 14 次方）：

- **16384 = 2¹⁴**
- 原因：
  1. **心跳包大小可控**：每个节点心跳带一张 16384 bit 的 slot 位图（2KB），太大太频繁会塞满带宽
  2. **不建议更大**：Redis 官方测试，**16384 足够支撑 1000 个 master 集群**（每个 master 处理 1000+ slot 已是大集群）
  3. **CRC16 哈希**：Redis 用 `CRC16(key) % 16384` 算 slot，16384 适合用位图索引
- **对比 65535（2¹⁶）**：心跳包要 8KB，官方选择**小且够用**的 16384

> ⭐ **金句**："**16384 是 2¹⁴，权衡了'够用 + 心跳包小'**——65535 心跳要 8KB 太重，16384 心跳 2KB 刚好够支撑 1000 master 集群。"

### ❓ Key 怎么找到节点？

> ↓ **答**（路由流程）：

1. 客户端连接任意节点 → 发 `GET key`
2. 节点算 `slot = CRC16(key) % 16384`
3. 看 slot 是不是归自己管：
   - 是 → 直接执行
   - 不是 → 看是不是在 **MOVED** 状态（已迁完）：
     - 是 → 返回 `MOVED slot new-node-address` → 客户端重连
   - 不是 → 在 **ASK** 状态（迁移中）：
     - 是 → 返回 `ASK slot new-node-address` → 客户端发 `ASKING` 转发到目标节点（**只这一次**）
4. 客户端缓存 slot → node 映射（**smart client**），下次直接路由

> ⭐ **金句**："**CRC16(key) % 16384 算 slot → MOVED（已迁）走重定向、ASK（迁中）走转发**——客户端缓存 slot 表后基本是 O(1) 路由。"

### ❓ 热 Key 怎么办？

> ↓ **答**（4 种方案）：

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **客户端本地缓存** | 客户端缓存热 key，不打 Redis | ✅ 最快；⚠️ 一致性差 |
| **多 key 分散** | `key_1, key_2, key_3` → 客户端随机挑一个 | ✅ 简单；⚠️ 改值要改所有 key |
| **读写分离** | 热 key 多 replica 分担读 | ✅ 简单；⚠️ 写还是单点 |
| **Slot 拆分** | 用 hash tag `prefix{tag}` 让 key 强制绑一个 slot | ⚠️ 治标不治本 |

> 实战推荐：**客户端本地缓存 + 多 key 分散**（大部分场景够用）

> ⭐ **金句**："**热 Key = 单 key 压力大**——解法：客户端缓存（治本） + 多 key 分散（治标）+ 读写分离（兜底）。"

### 📝 补充题

- **Q：为什么不用一致性 Hash？**
  > A：一致性 Hash 解决"加节点时数据迁移量最小"，但 Redis Cluster 是**预分片**（16384 slot），用 **CRC16 + 模 16384** 直接定位，简单且 O(1)。一致性 Hash 反而复杂。
- **Q：Slot 怎么迁移？**
  > A：`redis-cli --cluster reshard` → 选源节点 / 目标节点 / 迁移 slot 数 → 内部一条条 `MIGRATE` 原子迁移。**在线迁移**，业务无感。
- **Q：为什么 Cluster 不支持多 key 操作？**
  > A：`MGET` / `MSET` 的 key 可能不在同一 slot → 跨节点无法保证原子。解决：**Hash Tag**（`user:{1001}.name` 强制绑同 slot）。
- **Q：Cluster 怎么扩缩容？**
  > A：加新 master → `cluster meet` 握手 → `reshard` 迁 slot → 加 replica。缩容反过来。**全程在线**，不丢数据。

## 💡 第十组：性能下降怎么办？（调优/排查）

### ❓ Redis 性能突然下降怎么办？

> ↓ **答**（**按"现象→原因→解法"模板答**）：

#### Step 1: 定位现象（用 INFO + SLOWLOG）

```bash
redis-cli INFO stats       # 看 keyspace_hits/misses、instantaneous_ops_per_sec
redis-cli INFO memory      # 看 used_memory_human、mem_fragmentation_ratio
redis-cli INFO clients     # 看 connected_clients、blocked_clients
redis-cli SLOWLOG GET 10   # 看最近 10 条慢命令
redis-cli --latency        # 看延迟（持续模式）
```

#### Step 2: 对症下药（5 大常见原因）

| 现象 | 原因 | 解法 |
|------|------|------|
| **QPS 上不去 / 延迟变高** | 慢命令（KEYS * / HGETALL 大 hash / FLUSHDB）| 改 SCAN / 用 Lua 批量 / 拆分大 key |
| **内存持续涨** | 大 key（String > 10KB / Hash > 5000 字段）| `redis-cli --bigkeys` 查 → 拆分 |
| **某个 key 慢** | 热 key 单点 | 客户端本地缓存 + 多 key 分散 + 多 replica |
| **CPU 高** | 频繁 keys * / 持久化 fork 阻塞 / 大量过期触发 | 改用 SCAN / 关闭持久化 / 改 lazy + 异步删 |
| **连接数暴涨** | 客户端连接泄漏 | 客户端用连接池 / `CLIENT KILL` |

#### Step 3: 长期预防

- **大 key 监控**：`redis-cli --bigkeys` + 业务规范
- **热 key 监控**：`redis-cli --hotkeys`（基于 LFU 统计，4.0+）
- **慢命令监控**：SLOWLOG + 告警
- **内存告警**：使用率 > 70% 告警
- **不要用 KEYS * / FLUSHDB / MONITOR**（生产禁忌）

> ⭐ **金句**："**性能下降 = 先看 INFO 找现象 → SLOWLOG 找慢命令 → BIGKEYS/HOTKEYS 找大热 key → 对症下药**。日常监控：大 key + 热 key + 慢命令 + 内存。"

### 📝 补充题

- **Q：怎么发现 Big Key？**
  > A：① `redis-cli --bigkeys`（遍历所有 key，**生产慎用**会阻塞）；② `MEMORY USAGE key` 单查；③ RDB 分析工具 `redis-rdb-tools`；④ 业务规范（不让单个 value > 10KB）。
- **Q：怎么发现 Hot Key？**
  > A：① `redis-cli --hotkeys`（4.0+ 基于 LFU，**生产慎用**）；② 业务埋点统计访问次数；③ 客户端 proxy（Twemproxy/Codis）层统计。
- **Q：SLOWLOG 怎么配？**
  > A：`CONFIG SET slowlog-log-slower-than 10000`（10ms）+ `CONFIG SET slowlog-max-len 128`。生产推荐 5-10ms。
- **Q：客户端怎么优化？**
  > A：① **连接池**（go-redis 默认 10 × runtime.GOMAXPROCS）；② **Pipeline** 批量；③ **Lua 原子**；④ **避免大 key / 热 key**；⑤ **压缩 value**（msgpack/protobuf）。
- **Q：Redis 用 swap 了怎么办？**
  > A：紧急 `swapoff -a`（关 swap）/ 扩容 / 改 maxmemory 触发淘汰。**生产必关 swap**（`vm.swappiness=1`）。

## 🎁 加分题扩展（10 道选学题，真实面试高频但不算"必背"）

> 这一节是**加分项**——常规题答完后面试官追问的"偏题"，或者一些"高级特性"题。
> 建议：基础题答稳再来看，时间紧可跳过。

### ❶ Pipeline 是什么？和 Lua 区别？

> ↓ **答**：

**Pipeline（管道）**：
- **本质**：客户端把 N 个命令**打包一次性发到服务器**，减少 RTT（网络往返时间）
- 场景：批量写（`MSET` 不能原子但能批量）、循环 SET
- **不保证原子**：中途某个命令失败，**其他命令照常执行**

**Lua 脚本**：
- **本质**：服务器端**单线程执行整段脚本**，天然原子
- 场景：需要**多步原子操作**（CAS、分布式锁解锁）
- **保证原子**：脚本执行期间不会被其他命令打断

> ⭐ **金句**："**Pipeline 省 RTT 不原子，Lua 原子但不省 RTT（脚本要传到服务器）**。批量写用 Pipeline，复杂原子用 Lua。"

### ❷ Redis 事务（MULTI/EXEC）和 MySQL 事务区别？

> ↓ **答**：

| 维度 | Redis MULTI/EXEC | MySQL BEGIN/COMMIT |
|------|------------------|-------------------|
| 原子性 | **排队执行，但不支持回滚**（命令语法错才全失败）| 完整 ACID，支持 ROLLBACK |
| 隔离性 | **串行执行**（单线程天然隔离）| 多种隔离级别（RU/RC/RR/Serializable）|
| 持久性 | 看持久化配置（RDB/AOF）| 完整 WAL 机制 |
| 实现 | 命令入队 → EXEC 一并执行 | 日志/锁/MVCC 完整机制 |

> ⭐ **金句**："Redis 事务 = **串行化执行但不支持回滚**，MySQL 事务 = 完整 ACID。Redis 事务**只是批量执行**的语法糖，不能当 MySQL 用。"

### ❸ 什么是 Stream？和 Kafka 区别？

> ↓ **答**：

**Redis Stream**（5.0+）：
- **本质**：只追加的日志型数据结构（类似 Kafka topic）
- 命令：`XADD` / `XREAD` / `XGROUP` / `XACK`（消费者组）
- 支持**消费者组**、ACK、消息回溯
- 容量小（单机，内存受限）

**vs Kafka**：
| 维度 | Stream | Kafka |
|------|--------|-------|
| 吞吐量 | 几千~几万 QPS | 百万级 QPS |
| 持久化 | 内存 + AOF | 磁盘分段 |
| 消息回溯 | ✅ 任意 offset | ✅ 任意 offset |
| 消费者组 | ✅ | ✅ |
| 跨语言 | 弱 | 强 |
| 适用场景 | 轻量级消息流 | 大数据管道 |

> ⭐ **金句**："**Stream 是 Redis 内置的轻量级消息队列**——小流量可以，量大上 Kafka。Stream 比 Pub/Sub 强在**支持持久化和消费者组**。"

### ❹ Redis 6.0 ACL 权限控制？

> ↓ **答**：

- Redis 6.0 之前：只有一个 `requirepass` 全局密码，所有连接权限一样
- Redis 6.0+：**ACL**（Access Control List）：
  - 多个用户（`ACL SETUSER user1 ...`）
  - 每个用户独立密码 + 权限（`+@read` / `-@dangerous`）
  - 限制 key 命名空间（`~user:*`）
- 配合 `default user` 默认用户兜底

> ⭐ **金句**："**Redis 6.0 加 ACL 是为了多租户**——不同业务用不同账号 + 不同权限，比单一密码安全得多。"

### ❺ Redis 是 CP 还是 AP？

> ↓ **答**：

- **Redis 单机**：强一致（单线程串行），倾向 **CP**
- **Redis 主从**：默认**异步复制**，可能丢数据，倾向 **AP**
- **Redis Cluster**：异步复制 + 最终一致 → **AP**
- **Sentinel**：自动故障转移，可能脑裂 → **AP**

> ⭐ **金句**："**单机 Redis 是 CP（强一致）**，**集群是 AP（最终一致）**。CAP 三选二，Redis 选可用性 + 分区容错，放弃强一致。"

### ❻ Redis 怎么和 DB 同步双写？

> ↓ **答**（三种方案对比）：

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **同步双写** | 写 DB 同时写 Redis | ✅ 强一致；⚠️ 双倍延迟、Redis 挂了写失败 |
| **异步双写** | 写 DB → 异步队列 → 写 Redis | ✅ 解耦；⚠️ 中间有延迟 |
| **binlog 订阅**（**推荐**）| Canal 订阅 MySQL binlog → 同步到 Redis | ✅ 完全解耦；⚠️ 引入中间件 |

> ⭐ **金句**："**生产推荐 Canal 订阅 binlog**——把同步从业务里解耦出去，DB 仍是事实来源，Redis 只是缓存层。"

### ❼ Redis 客户端重连机制？

> ↓ **答**（设计要点）：

1. **连接池**：用 `redis.Pool`（go-redis）自动管理连接
2. **自动重连**：客户端底层自动重连（`MaxRetries`）
3. **重试 + 退避**：失败后**指数退避**重试（1s/2s/4s/8s）
4. **熔断**：连续失败 N 次 → 熔断 → 直接返回错误，不连 Redis
5. **超时控制**：每次命令都有超时（`DialTimeout` / `ReadTimeout` / `WriteTimeout`）

> ⭐ **金句**："客户端要**连接池 + 超时 + 退避重试 + 熔断**四件套，缺一不可。光重试不熔断会把 Redis 打死。"

### ❽ Redis 7.0 新特性（FUNCTION / Sharded Pub-Sub / Client-Side Caching）？

> ↓ **答**：

| 特性 | 作用 |
|------|------|
| **FUNCTION** | 服务器端函数（类似 Lua 但更强大，支持库、持久化）|
| **Sharded Pub-Sub** | Cluster 下**按 slot 分片**的发布订阅，避免全局广播 |
| **Client-Side Caching** | 客户端缓存（Tracking），Redis 主动通知 key 失效 |
| **listpack 全面替代 ziplist** | 消除级联更新（Hash/Set/ZSet 内部）|
| **Multi-part AOF** | AOF 拆成 base + incr + history 三段，恢复更快 |
| **LFU 优化** | 计数器位数增加，热点识别更准 |

> ⭐ **金句**："**Redis 7.0 是大版本**——listpack 替代 ziplist、Sharded Pub-Sub、Client-Side Caching、Multi-part AOF，每个都是面试加分点。"

### ❾ Redis 大 key 删除会怎样？怎么删？

> ↓ **答**：

**问题**：
- `DEL bigkey` → **同步阻塞**主线程数秒（取决于大小）→ 整个 Redis 卡顿
- 阻塞期间所有命令排队 → 连接打满 → 雪崩

**解法**：

| 方法 | 做法 |
|------|------|
| **`UNLINK key`**（4.0+）| **异步删除**——主线程立刻返回，后台线程慢慢删 |
| **`FLUSHDB ASYNC` / `FLUSHALL ASYNC`** | 同上，异步清库 |
| **分批删** | 大 List：`LPOP` 一批 + `SLEEP` 几 ms，循环 |
| **大 Hash 分批删** | `HSCAN` + `HDEL` 一批 + 循环 |

> ⭐ **金句**："**大 key 绝对不能直接 DEL**——会阻塞主线程几秒。**用 UNLINK 异步删**，或 HSCAN 分批删。"

### ❿ Redis 在微服务里怎么用？

> ↓ **答**（最佳实践）：

- ✅ **缓存读多写少**（用户资料、商品详情、配置）
- ✅ **分布式锁**（订单、库存、幂等）
- ✅ **限流**（滑动窗口、令牌桶）
- ✅ **Session / Token** 共享
- ✅ **排行榜 / 计数器** / **延迟队列**
- ✅ **服务间解耦**（Pub/Sub 通知）
- ❌ **不要当 MySQL 用**（大数据量 + 事务）
- ❌ **不要当 Kafka 用**（高吞吐消息流）
- ❌ **不要当 ES 用**（全文搜索）
- ❌ **不要持久化关键数据**（至少不要只依赖 Redis 持久化）

> ⭐ **金句**："**Redis 是瑞士军刀不是主力仓库**——缓存 + 锁 + 限流 + 排行 + 计数 + 延迟队列都能干，但**核心业务数据还在 DB**，Redis 只做加速层。"
